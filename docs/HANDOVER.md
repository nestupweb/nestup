## What this is
**NestUp** — my final project for RUNI "Internet Technologies — Become a Full-Stack Engineer" (assignment PDF: `Internet Technologies (2).pdf`, **due 2026-09-06**). Two-sided shared-apartment / roommate matching: seekers browse rooms and swipe, hosts post rooms, chat is in-app (whole household in one thread), viewings are proposed and approved inside the chat. Two compatibility scores (Lifestyle + Social/shared interests). **The swipe deck shows only high matches** (combined score ≥ `MIN_DECK_SCORE` = 60 in `lib/swipe.ts`, deck cap 60); elsewhere scores only inform and sort.

  - **The demo addresses were invented, so they were replaced (2026-08-28).** The seed made street names up ("HaTamar 37, Jaljulia"), and most don't exist — which is why ~334 rooms never geocoded and used to be scattered around their city centre. `npm run addresses:real` (`scripts/real-addresses.mjs`) fixes the *address* instead of faking the position: for each town it asks OpenStreetMap what streets are actually there and gives each unplaceable room either a real addressed building (street + house number, pinned on the building) or a real street (pinned on one of the street's own mapped vertices, with no house number, because the door number is the part we don't know). City, rent, photos, owner and description are untouched. It writes `street`/`house_number` as well as the legacy `address` column, and everything it places is `coords_source: 'geocoded'`.
    - It reads **Overpass** first and caches each town in the OS temp dir, so a re-run is free. Overpass will cut you off after a few hundred queries — it did, halfway through this very job, and stayed blocked for the rest of the day — so there is a **Nominatim reverse-geocoding fallback**: sample points spread across the town (deterministically, golden angle), ask "what is here?" at 1 req/s with `Accept-Language: en`, and keep the road and the coordinates *it* returns. Slower (~30 s a town), but it always answers.

  - **Geocode in bulk with Photon, not Nominatim.** Nominatim allows one request a second and *no* parallel requests, which put 800 rooms two hours away — and asking anyway doesn't fail loudly: the extra requests come back empty and every room quietly lands on its city centre (the first run of this script placed 25 rooms in a row on city centres before that showed up in the tally). `scripts/geocode-listings.mjs` uses photon.komoot.io — same OSM data, no such limit, ~150 rooms a minute, and it takes a bounding box so a query can't match the other end of the country.

Two guards make that safe: a **`listings_owner_is_permanent` trigger** refuses any change to `owner_id` (without it a co-owner could set it to themselves and RLS would allow it — they pass the household test both before and after, and `with check` cannot see the old row), and a **household SELECT policy** so a co-owner can still read the room once it is paused or taken (otherwise `remove_listing`'s own SELECT comes up empty and reports "already gone"). **Every listing write now scopes by `id` alone and checks `.select("id")` for zero rows** — RLS refusing a row returns no error, which would otherwise read as a silent success. `saveListingAction` stopped writing `owner_id` on update. ## Known gotchas
- **A filter applied in JS over a capped query is a time bomb.** `getSwipeDeck` fetched the newest 300 active rooms and *then* filtered them to the seeker's cities and budget. That was fine at 155 listings; the third seed wave took it to 491, and 352 rooms are now newer than the newest Tel Aviv room — so a Tel Aviv seeker's window contained none of their own city and the deck came back empty. To the user that reads as "the matching is broken", not as a query bug. Anything that narrows results must narrow them **in the query** (`.in`/`.gte`/`.lte`), with the cap applied after. Same shape to watch for anywhere a `.limit()` sits upstream of a `.filter()`.
- **Chunk every `.in()` that spans the whole seed set.** PostgREST puts the list in the query string, so 813 owner UUIDs build a ~30 KB URL and the request dies with a bare `TypeError: fetch failed` — no status, no message worth reading. `scripts/seed.ts` chunks at 80 (`CHUNK`), and `addRoommates` is the one that broke before it did.
- **A new PERMISSIVE RLS policy can only widen, never hide.** Postgres OR's permissive policies, so adding one to let a few people read something silently re-grants whatever another policy was taking away. This bit us for real: 0027's `linked_to_listing` re-opened rooms that 0030 hides from blocked/suspended members, and it only showed up in one direction (fixed in 0031). Anything meant to *hide* must go into **every** permissive policy on the table, or be declared `as restrictive`. Test both directions of a symmetric rule — one-way passes are how this hides.
- **Delete Listing does not delete the row, on purpose (0028).** A real delete cascades to the conversations about the room and every message in them, so the people who wrote them would lose them and the notice sent on the way out would be destroyed with the thread. `remove_listing()` stamps `listings.removed_at` instead: gone from Listings, Swipe, the owner's profile, Liked, History and its own page, one way, chats kept. **Every owner-facing listings query must carry `.is("removed_at", null)`** — `profile`, `listing`, `settings`, `browse/[id]` and `browse/[id]/chat` do; Liked/History filter it in JS after the join.
- **A room that leaves the site must not take its chats with it.** `active listings are public` (0001) is `is_active or owner_id = auth.uid()`, and `my_conversations()` inner-joins listings — so pausing or closing a room used to delete every seeker's chat about it from their inbox. `0027` adds a second SELECT policy, `linked_to_listing(id)` (SECURITY DEFINER so it cannot recurse through the conversations policies), letting seekers-in-a-conversation and residents keep reading that one row. Browse, Swipe and the people pages filter `is_active = true` in the query, so nothing closed leaks into them. If you add a listings query that relies on RLS alone to hide inactive rooms, it will now see these.
- **Never write `<form action={formAction}>` for a server action.** React 19 resets an uncontrolled form the moment the action returns, so a validation error throws away everything the member typed (measured: the field's value becomes `""`). Use `useStickyForm` from `@/lib/hooks`: `const [state, form, pending] = useStickyForm<State>(action, {})` then `<form {...form}>`. It keeps `action` on the element as the no-JS fallback. Verified live 2026-08-27 on signup › onboarding and the listing form.
- **`server-only` is not on disk** — Next aliases it internally, so Vitest cannot resolve a module that imports it. `vitest.config.mts` aliases it to `tests/stubs/server-only.ts`; keep that if you add another server-only module.
- **E-mail templates the app sends must be TS modules, not `.html` files.** Vercel traces imports, not runtime `readFileSync` paths, so a template read from disk does not survive the build — hence `lib/email/new-match.ts`. `supabase/templates/` is only for the templates Supabase itself renders.
- Test runs must go through `npm test` (it sets `NODE_OPTIONS=--no-experimental-webstorage`). A bare `npx vitest` lets Node 25's own `localStorage` shadow jsdom's and `theme-toggle.test.tsx` fails with `localStorage.clear is not a function`.
- `grep -r` over the folder crawls `node_modules` on OneDrive and times out — use the Grep tool with `!{node_modules,.next}/**` or targeted paths.
- Many files have CRLF; when editing with Node scripts normalise `\r\n` first (the Edit tool is fine).
- Stale `.next/dev/types` can break `tsc` — delete `.next/dev` when no dev server runs.
- Frozen TDD test files (`filter-bar`, `listing-query`, `listing-gallery`, `interests-picker`, `redirect`) — never weaken them to make code pass.
- Mac "nav opens a new tab" report (friend) was not reproducible in Chromium or WebKit; the manifest was added for Safari "Add to Dock"/iOS home-screen scope. If it recurs, get the exact URL and whether it's a Dock app before changing code.
