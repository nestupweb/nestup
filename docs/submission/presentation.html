Product · The problem

Finding a flatmate isn't a search problem

The listings are easy to find — Facebook groups, Yad2, WhatsApp. They all index the apartment: rent, rooms, square metres, neighbourhood.

But everything that actually decides whether a shared flat works — when people sleep, how often guests come over, whether the kitchen gets cleaned, whether the flat keeps Shabbat — is missing, or buried in free text nobody can filter on.

So both sides do the filtering manually, after the expensive step.

The seeker

Messages 30 listings. Gets 8 replies. Visits 4 flats. Discovers the mismatch in person — after crossing the city.

The household

Fields dozens of "hi, still available?" messages. Repeats the same screening questions. Still meets people who were never going to fit.

The second, quieter problem: a conversation starts with one roommate — whoever posted — but the decision belongs to the whole household. Everyone else hears a summary. That's why NestUp treats the household as the counterparty, and it's the differentiator to come back to on the flows slide.

Product · Users

Two sides, one account

Side A

The Seeker

  • 22–35: students, young professionals, relocating
  • Scarce resource: time and travel — each visit costs an evening
  • Fear: a year with people they can't live with

Side B

The Household

  • An existing flat with a room to fill
  • Scarce resource: attention — they can't interview forty people
  • Fear: a bad roommate they're then stuck with

The same person is a seeker one year and a household the next. One account does both, with no mode switch.

If asked "who's the customer?": user and customer are the same person today, and the product is free — a two-sided marketplace has no value to either side until it has liquidity on both, so charging early suppresses the thing that makes it work. The side you'd build toward is the household: an empty room is rent someone pays out of pocket every month. That's the urgency and the willingness to pay.

Nothing charges anyone today, and the schema and ranking function would both need to change. Say that plainly rather than implying it exists.

Product · Main flows

Discover → match → meet

Seeker

  • Browse without an account — 13 filters, sort, map
  • Build a profile — budget, cities, dates, daily life, interests
  • Swipe a ranked deck of strong matches only
  • Chat with the whole household at once
  • Schedule a viewing inside the thread

Household

  • List a room — geocoded address, photos, rules
  • Tag roommates — each accepts and becomes a co-owner
  • Receive interest in one inbox
  • Screen with a real compatibility score
  • Close the room — taken, paused, or removed; chats survive
Out of scope on purpose — say this before they ask: no payments, no lease contracts, no identity verification, no native app, no learned recommender. Ranking is a deterministic scoring function: explainable, testable, debuggable. At this stage that's worth more than being marginally better.

Architecture

The browser is never a trusted client

Browser
Server Components render to HTML. Client Components for interaction only. Realtime socket. MapLibre, loaded on demand.
Vercel — Next.js runtime
proxy.ts edge auth gate · Server Actions for every write · Cache Components (use cache / use cache: private)
Supabase — Postgres 17
21 tables, RLS on every one · 36 SQL functions · Auth · Storage · Realtime

Every read goes through a Server Component, every write through a Server Action — and underneath both, Postgres decides what the caller may actually see.

Authorisation is enforced in the database, not in application code. A bug in a page, an action, or a cache cannot leak another member's data — the leak would have to get past Postgres first.

Why this stack, if asked one by one: Next.js App Router — Server Components mean a 20-room list ships HTML, not JSON plus a client fetch; Server Actions remove a hand-written API layer for every mutation. Supabase — Postgres with RLS is the reason; auth, storage and realtime in one product removes three integrations. Zod — one schema gives both validation and the TypeScript type, so they can't drift. MapLibre + CARTO — keyless, and the worker is self-hosted, so no map vendor key and no third-party CDN at runtime.

Architecture · Data

21 tables, and three that can't be written

Core: profiles · listings · listing_residents · conversations · messages · viewings · swipes

profiles.user_id is the primary key and a foreign key to auth.users. No separate profile id — so every RLS policy is a comparison against auth.uid() with no join, and deletion cascades correctly by construction.

Two tables for one person. profiles is member-readable; profile_details (phone, contact email) is owner-only. Splitting them makes a new private column private by default, not by remembering.

Soft deletion. A removed room must not take its conversations with it — people who talked about a room still have that history.

36SQL functions
20indexes, 6 of them partial

Denormalisation, if asked: household_size and household_gender live on listings, maintained by triggers over listing_residents. The browse filter and the deck both need them on every row; computing per row would turn one query into 800. Write cost for read benefit — right way round, because rooms are read far more often than households change.

Security · The pattern I'd defend hardest

No write policy at all

Three tables — suspensions, listing_invites, app_config — have no insert, update or delete policy whatsoever.

They're written only by SECURITY DEFINER functions: apply_report_suspension(), invite_listing_roommates(), respond_to_listing_invite().

When a table must only ever be written one way, give it no write policy and one function. Then there is no path to a wrong write — rather than a policy trying to enumerate every wrong write and maybe missing one.

The concrete consequence

A member cannot lift their own suspension. Not because a policy forbids it — because no route to that write exists.

Ownership can't be stolen either

A trigger refuses any plain UPDATE of listings.owner_id. The one legitimate case — handing a shared room to a roommate when an account closes — happens inside delete_own_account(), which sets a transaction-local flag nothing else in the schema sets.

Follow-up worth volunteering: deleting an account used to cascade the listing away — which, once listings could be co-owned, meant deleting a home out from under the roommates living in it. Now it hands the room over first, in the same transaction, and refuses to hand it to a roommate who already has a live room of their own (a unique index would reject it anyway).

A missing preference scores ~60%, not zero

"I didn't say" is not "we disagree". Scoring it as a mismatch would punish incomplete profiles and make the deck reward form-filling instead of fit.

Scoring is directional

Each side judges their preferences against the other's reality. Seeker→room and room→seeker are different questions.

The gate is the product decision

Below a combined 60, a room never enters the deck. That's why a deck can legitimately be empty — and why "no strong matches yet" had to be designed, not treated as an error.

If asked why the module is split in two: lib/swipe.ts is imported by client components, so it must be safe in a browser bundle; lib/swipe-deck.ts is server-only and holds the cookie-reading Supabase client. That's a real constraint, not tidiness — it was a build error first.

Scale · Measured, not asserted

Why returning to a tab was slow

Next's App Shell prerender advances through cached reads and stops at the first uncached one.

Every page began with an uncached auth.getUser() — a network round-trip to Supabase. That single call kept everything behind it out of the prefetch, no matter how well cached it was.

Caching that identity read removed ~300 ms from each tab. Three of four tabs now make zero server requests on return.

TabBeforeAfter
Swipe860 ms69 ms
Chat1900 ms71 ms
Profile370 ms69 ms
Listings850 ms375 ms

Warm cache, measured on production with Playwright. Skeleton gone entirely on the first three.

The honest part — say it. Listings still flashes a skeleton. I traced it: zero server requests, no long JS tasks. With the page-slide animation suppressed the skeleton drops from 296 ms to 61 ms — so it's the view transition holding a frame that happens to contain the skeleton, not a data wait. I also tried a fix that measurement disproved (a second, argument-free listings query) and removed it rather than leave unjustified complexity in the busiest page.

Scale · State

No state library. On purpose.

Kind of stateWhere it lives
Server dataServer Components — rendered output, not client state
Cached server dataCache Components, invalidated by tag
Form stateuseActionState — a rejected form keeps what you typed
Ephemeral UIuseState
Filters, sort, page, tabThe URL — shareable and back-button correct
RealtimeA subscription that drops a cache tag; the server re-renders

Redux or React Query would mean maintaining a second copy of the server's data with its own invalidation rules. The tag system already does that job, in one file, with the server as the single source of truth.

Blast radius is a tested rule

Mutations used to answer every write with a fistful of revalidatePath calls — so editing a room threw away your chats and profile too. Now a write invalidates only what it changed, and a test fails if that regresses.

The interesting case: a member's chat inbox changes when someone else writes, and no action of theirs runs. The Realtime socket calls a Server Action that drops their own tag. That's what makes caching an inbox safe rather than stale — and it's why the inbox could finally be cached at all, having been deliberately left uncached before.

Testing

What "working" means, and what I didn't test

The product fails in three ways, in descending cost:

  • A member sees another member's data. Unrecoverable — the trust proposition dies.
  • A core flow silently does the wrong thing — a message that doesn't arrive, a swiped room that comes back.
  • A screen is wrong or ugly. Embarrassing, cheap to fix.

The suite is weighted to match. Access control and business rules are tested hard; presentation is tested where it encodes a rule, not for its appearance.

740tests, all passing
124cities re-measured for deck coverage on every run

Name a gap before they find it: the unit suite mocks the Supabase client, so RLS policies themselves aren't exercised by it — they're covered by real-browser checks and review. The fix I'd build is a test running real queries as two different members against a test project. Also: no full end-to-end journey, email delivery mocked, and load never measured — the scale reasoning is analytical.

Security

Four layers, and one disclosed trade-off

1 · Edge proxy
Refreshes the session, redirects unauthenticated page requests. Pages only — an API caller gets a JSON 401, not an HTML redirect.
2 · Page gate
Redirects on no session, and on a suspended account.
3 · Server Action
Every write begins with an uncached check.
4 · Row Level Security
The one that matters. 72 policies. Assumes all three above have failed.

The trade-off I chose

Identity is cached for rendering, 300 s — which is what removed the ~300 ms skeleton. Cost: a suspension takes effect within that window instead of on the next page. The check isn't removed; it refreshes less often.

What it doesn't cost: the edge gate is still uncached on every request, every write still uses the uncached check, and RLS is untouched. A test fails if any action ever calls the cached reader.

Signing out is a security operation. It posts to a Route Handler answering 303, not a Server Action redirect — because a soft redirect leaves the browser's private caches and rendered pages alive, one back-button press away, and the next person to sign in on that computer inherits the tab in that state. Only a full document load empties them. Verified on the live site. POST-only, so no cross-site <img> can log someone out.

Reflection

What I'd do with more time

Would fix first

  • RLS policy tests — real queries as two members. The one layer the suite can't reach.
  • Rate limiting on writes — only auth email is throttled today.
  • Deck scoring into SQL — fine at 824 rooms, wrong shape at 50,000.
  • A real moderation queue — the suspension function exists; nothing calls it on a threshold.

Known limits, stated plainly

  • No identity verification. Email confirmation only — and members meet in person. The largest real-world risk, and not solvable with code alone.
  • Realtime connection caps are the first ceiling, before CPU or storage.
  • No observability. Problems would be found by a person noticing.
  • Backups are untested. An untested backup is a hope, not a plan.
Don't rush this slide. The assignment says the project is judged on quality of thinking, not feature count — this is where that's demonstrated. Being specific about limits reads as command of the system; a claim of full coverage reads as not having looked.
